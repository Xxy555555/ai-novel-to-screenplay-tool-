# 产品需求文档（PRD）——「ScriptForge」AI 小说转剧本工具

> 版本：v1.0 ｜ 日期：2026-06-05 ｜ 状态：评审中
> 一句话定位：把 3 章以上的小说，一键转换为**结构化、可校验、可视化编辑**的剧本初稿（YAML）。

---

## 0. 文档目的

本 PRD 定义参赛作品「ScriptForge」的产品目标、用户、范围、功能、亮点与验收标准，作为后续设计文档（YAML Schema 设计文档）、技术实现与现场演示的统一依据。

---

## 1. 背景与问题（Why）

### 1.1 行业痛点
- 大量网文/小说作者希望把作品改编成剧本（影视、漫剧、有声剧、短剧），但**剧本写作门槛高**：格式专业、规则繁琐、需要把"叙述"重构为"可拍摄的画面与对白"。
- 人工改编**慢且贵**：一部作品的初稿改编往往需要专业编剧投入数周。
- 现有 AI 工具大多只能做"续写/润色"，**缺乏从长篇小说到结构化剧本的端到端能力**，且输出是难以二次编辑的纯文本。

### 1.2 真正的难点（也是本作品的技术立意）
"小说 → 剧本"不是翻译，而是一次**结构化重构**。难点集中在题目所要求的"**3 章以上**"：

| 难点 | 说明 |
|------|------|
| 跨章角色一致性 | 同一角色在不同章节有不同称谓（"林深 / 林先生 / 他 / 师兄"），分块处理极易被认成不同人、口吻前后矛盾 |
| 场景切分 | 一章 ≠ 一场戏，需按"时间 + 地点 + 在场人物"切分 |
| 对白归属 | 谁说的、带什么情绪/动作，原文常为隐式 |
| 叙述→影像 | 剧本"只演不说"，心理描写要转成画外音（V.O.）或可拍动作 |
| 结构合法性 | 输出必须是 Schema 合法、可机器校验、能自动修复的 YAML |

> **产品主张**：谁能显式地解决这 5 个难点，谁的工具才真正可用。本作品的架构每一层都对应一个难点。

## 2. 目标与成功指标（Goals & Metrics）

### 2.1 产品目标
1. 让非专业作者**在数分钟内**获得一份结构清晰、可继续打磨的剧本初稿。
2. 输出**结构化 YAML**，既能被机器校验，又能被人手动编辑、用 git 管理。
3. 提供**可视化编辑 + 质量评分**，让作者快速判断与修订改编质量。

### 2.2 成功指标（用于自评与现场展示）
| 指标 | 目标 |
|------|------|
| Schema 合法率 | 经自动修复后 100% 通过 `screenplay.schema.json` |
| 对白说话人归属覆盖率 | ≥ 90% |
| 角色一致性（别名消解，无悬空引用） | ≥ 95% |
| 场景头三要素完整率（内外景/地点/时间） | ≥ 90% |
| 3 章示例端到端生成耗时 | 可接受范围内，且全程有进度可见 |

## 3. 目标用户与场景（Who & When）

- **主要用户**：网文/小说作者、改编工作室助理、编剧学员。
- **次要用户**：短剧/漫剧脚本策划、影视开发前期评估人员。
- **核心场景**：作者拿到自己 3+ 章小说 → 上传 → 一键生成剧本初稿 → 在线微调对白/场景 → 导出可读剧本与 YAML，交给专业编剧继续打磨。

**用户故事**
- 作为作者，我希望上传小说后能看到 AI 一步步把它拆成场景与对白，这样我信任它的产出。
- 作为作者，我希望角色名字在全篇保持一致，而不是同一个人被拆成好几个。
- 作为作者，我希望直接在界面上改对白，并即时看到 YAML 同步变化。
- 作为作者，我希望有一个"改编质量分"，告诉我哪里还需要人工补。

## 4. 范围（Scope）

### 4.1 本期做（In Scope）
- 小说 txt 上传 / 选择内置示例（中英双语）。
- 规则法章节切分 + 三阶段 AI 管线（理解 → 生成 → 质检）。
- 角色圣经（跨章一致性引擎）。
- 结构化剧本 YAML 输出 + JSON Schema 校验 + 自动修复。
- 改编质量报告/评分。
- 实时进度流（SSE）。
- 可视化剧本编辑器（场景卡片 / 角色面板 / Monaco YAML 双向同步）。
- 可读剧本预览（Fountain 风格）+ 导出（YAML / 文本）。
- 分镜 / 情绪 / 节奏标注层（差异化亮点）。

### 4.2 本期不做（Out of Scope）
- 用户账号体系、云端持久化、协同编辑。
- 自动配音 / 分镜出图 / 视频生成。
- 移动端适配（聚焦桌面演示）。
- 导出 PDF 为加分项，时间允许再做。

## 5. 功能需求（Functional Requirements）

> 优先级：P0 必做 / P1 重要 / P2 加分

### 5.1 输入与章节切分（P0）
- F1：支持上传 `.txt` 小说或选择内置示例。
- F2：自动识别章节边界（`第X章` / `Chapter X` / 标题行启发式），要求 ≥ 3 章。
- F3：对超长文本按"场景/段落边界 + 块大小"分块，避免硬截断破坏语义。

### 5.2 三阶段 AI 管线（P0）
- F4 理解层 Analyze：分块抽取"故事事实"——场景（地点/时间/在场人物/事件）、对白（说话人+台词+情绪）、叙述节拍。
- F5 角色圣经：每块处理后渐进更新角色注册表（合并别名、关系、口吻），并回填给下一块作上下文（**跨章一致性核心**）。
- F6 生成层 Compose：把结构化事实生成剧本 YAML——场景头、动作行、对白块、转场、心理→V.O.。
- F7 质检层 Validate：JSON Schema 校验；不合法时把错误回喂 LLM 修复（限次），仍失败走规则兜底。

### 5.3 质量报告（P1）
- F8：输出可量化指标——Schema 合法率、对白覆盖率、角色一致性、场景完整率、"演 vs 说"比、结构统计；并给综合评分。

### 5.4 可视化编辑（P1）
- F9：场景卡片视图，展示/编辑场景头、在场角色、元素流（动作/对白）。
- F10：角色面板，可视化角色圣经（名字、别名、关系）。
- F11：Monaco YAML 编辑器，与卡片**双向同步**（改一边另一边更新）。
- F12：编辑后可重新校验，实时反馈是否仍 Schema 合法。

### 5.5 预览与导出（P1）
- F13：Fountain 风格可读剧本预览（接近真实剧本排版）。
- F14：导出 YAML / 纯文本剧本；（P2）导出 PDF。

### 5.6 实时进度（P1）
- F15：生成过程通过 SSE 推送阶段进度与中间产物，前端进度条逐步展示。

### 5.7 分镜/情绪/节奏标注（P2 差异化亮点）
- F16：每场戏附情绪基调、节奏标签、镜头/机位建议，让初稿"有导演感"。

## 6. 技术方案概览（How，详见技术计划与 Schema 设计文档）

### 6.1 架构
```
小说 txt
  ├─[0] 章节切分（规则法）
  ├─[A] 理解层 Analyze ──┐
  │                      ├─ ★角色圣经 / Story State（跨章一致性）
  ├─[B] 生成层 Compose ──┘
  ├─[C] 质检层 Validate（Schema 校验 + 自动修复 + 质量评分）
  └─[D] 编辑层（前端：卡片 / YAML 双向 / 预览 / 评分 / 导出）
```

### 6.2 技术栈
- 前端：Vue3 + Vite + Pinia + Naive UI + Monaco Editor；SSE（EventSource）。
- 后端：Java 17 + Spring Boot 3；Jackson YAML 序列化；networknt json-schema-validator。
- AI：**通用大模型适配器**（详见 6.4）。

### 6.4 通用大模型适配器（一个适配器，换配置即切换任意模型）
- **设计目标**：不为每个厂商写一套对接代码，而是用**一个通用适配器**，通过 `(base-url + model + api-key)` 三个配置切换任意模型；不绑定单一厂商。
- **实现依据**：市面绝大多数大模型都提供 **OpenAI 兼容的 `/chat/completions` 接口**，因此一个 OpenAI 兼容适配器即可覆盖：OpenAI、DeepSeek、Kimi（月之暗面）、智谱 GLM、通义千问、本地 Ollama/vLLM，以及 OpenRouter/one-api 这类聚合网关。
- **切换方式**：
  - 一般厂商：改 `base-url + model + api-key` 三个配置即可换模型；
  - 聚合网关（OpenRouter/one-api）：base-url 与 api-key 固定，**仅改 `model` 一个字段**就能在上百个模型间切换。
- **三种 provider**：
  - `openai`：通用 OpenAI 兼容适配器（推荐，覆盖几乎所有模型）；
  - `claude`：原生 Anthropic Messages API（报文格式不同，单独适配）；
  - `stub`：规则桩，无 Key 也能离线跑通全流程（现场演示零依赖，默认）。
- **接入示例**（设置对应 base-url/model 即可）：
  | 厂商 | base-url | model 示例 |
  |------|----------|-----------|
  | OpenAI | `https://api.openai.com/v1` | `gpt-4o` |
  | DeepSeek | `https://api.deepseek.com/v1` | `deepseek-chat` |
  | Kimi | `https://api.moonshot.cn/v1` | `moonshot-v1-8k` |
  | 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | `glm-4` |
  | 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
  | OpenRouter（聚合） | `https://openrouter.ai/api/v1` | 仅改此字段即可换模型 |
  | 本地 Ollama | `http://localhost:11434/v1` | `qwen2.5` |
  | Claude（原生） | `https://api.anthropic.com` | `claude-opus-4-8` |
- **配置位置**：`application.yml` 的 `scriptforge.llm.*`，全部支持环境变量覆盖（`SCRIPTFORGE_LLM_*`），无需改代码、无需重新编译即可切换模型。

### 6.3 YAML Schema（概览，详见 `docs/yaml-schema-design.md`）
顶层：`meta`（元信息）/ `characters`（角色注册表）/ `scenes`（场景序列）/ `report`（质量报告）。
场景内 `elements` 为**有序异构元素流**（action / dialogue / voiceover / transition / montage），还原剧本"页面"。

## 7. 非功能需求（Non-Functional）

- **可用性**：无 API Key 也能用规则桩跑通全流程（现场零依赖演示）。
- **健壮性**：LLM 输出经 Schema 校验 + 自动修复，保证 100% 合法 YAML。
- **可读性/可维护性**：输出 YAML 人类可读、可手改、可 git diff。
- **国际化**：中英双语小说均支持。
- **性能**：3 章示例端到端可在合理时间内完成，且全程进度可见。
- **编码**：全链路 UTF-8，正确处理中文。

## 9. 风险与对策（Risks）

| 风险 | 对策 |
|------|------|
| LLM 输出不合法/不稳定 | 两阶段分离 + Schema 校验 + 自动修复循环 + 规则兜底 |
| 跨章角色被拆分 | 角色圣经渐进实体消解，别名归并到统一 id |
| 现场无网络/无 Key | 内置规则桩 LLM，离线可演示完整流程 |
| 中文编码问题 | 全链路强制 UTF-8 |
| 范围过大拖垮完成度 | 分镜/PDF 等设为 P2，可选扩展，Schema 预留字段 |

---

## 10. 验收标准（Acceptance）

1. 上传/选择 ≥ 3 章小说，能端到端生成 Schema 合法的剧本 YAML。
2. 同一角色跨章节保持同一 id（别名正确归并）。
3. 前端可视化编辑，卡片与 YAML 双向同步，重新校验通过。
4. 展示改编质量评分与各项指标。
5. 可导出 YAML 与可读剧本文本。
6. 交付 `docs/yaml-schema-design.md`，逐字段说明 Schema 设计原因，且与 `screenplay.schema.json` 一致。

## 11. 竞赛亮点速览（Pitch）

1. **角色圣经 / 跨章一致性引擎** —— 直击"3 章以上"题眼的杀手锏。
2. **三阶段管线（理解→生成→质检）** —— 鲁棒、可解释、可展示中间产物。
3. **Schema 驱动 + 自动修复** —— 输出 100% 合法，呼应"可校验/可编辑"目标。
4. **改编质量报告/评分** —— 量化、专业，给评委可看的数据。
5. **可视化编辑器 + YAML 双向同步** —— 现场 wow 点。
6. **可读剧本预览（Fountain 风格）** —— 把 YAML 还原成作者认得的剧本样子。
7. **分镜/情绪/节奏标注层** —— 让初稿"有导演感"，区别于普通转写。
8. **通用大模型适配器** —— 一个适配器、换配置即切换任意模型（OpenAI/DeepSeek/Kimi/GLM/通义/本地/聚合网关），不绑定厂商。
9. **中英双语 + 离线可演示** —— 适用面广、演示零风险。
